# 项目二：百万级日活图像生成服务 架构师落地 Checklist
**定位**：架构师视角 · 按周拆解 · 含里程碑/核心交付/关键决策/风险卡点/验收标准  
**技术栈对齐**：tRPC + Next.js + Temporal + Postgres + AWS GPU（5090/H100/B200）

---

## Phase 1：Week 1 —— 端到端链路打通（从0到1）
**核心里程碑**：完整跑通「tRPC提交 → Temporal编排 → GPU调度 → 模型推理 → 结果存储 → 状态回调」全链路，具备基础生图服务能力。

### 1. tRPC 接入层（Next.js 承载）
#### 核心交付
- 定义3个核心Procedure，形成统一接入规范：
  - `image.generate`：Mutation，提交生图任务，入参经Zod强校验
  - `image.getStatus`：Query，查询任务状态与结果
  - `image.subscribe`：Subscription，实时推送生成进度与状态变更
- 落地3个公共中间件：鉴权校验、请求全链路日志、统一错误码规范
- 接入层部署：AWS ECS 无状态部署，支持水平扩容
#### 关键技术决策（架构师必须拍板）
- **批量请求策略**：启用 `httpBatchLink`，设置单批最大请求数=10、最大等待窗口=50ms，平衡连接数与延迟
- **流式实现选型**：Subscription 采用 WebSocket 长连接（而非SSE），匹配AWS API Gateway的WebSocket支持，降低延迟
- **限流粒度**：按「API Key + 用户ID」两级令牌桶限流，优先保障高等级用户
#### 风险卡点
- 批量请求导致单请求体过大、网关超时 → 强制设置单批payload上限，超时自动拆批
- Subscription 长连接数过载 → 提前评估连接数容量，配置连接数阈值告警，触发时扩容接入层
#### 验收标准
- tRPC 客户端可正常提交任务、查询状态、接收进度推送
- 参数错误在接入层100%拦截，不向下游透传无效请求
- 接入层水平扩容后QPS线性提升

### 2. Temporal 任务编排层
#### 核心交付
- 定义 `ImageGenerationWorkflow` 标准工作流，包含4个核心Activity：参数校验、调度分发、推理执行、结果落库
- 配置幂等规则：以 `client_request_id` 为幂等键，重复提交直接返回已有任务
- 配置重试与超时策略：GPU故障/超时自动重试（最多3次，指数退避），参数错误/内容违规不重试
- Temporal 集群部署：优先采用 Temporal Cloud 托管服务，减少运维成本
#### 关键技术决策
- **状态机统一**：全链路只以 Temporal 的任务状态为准，业务层不单独维护状态，避免数据不一致
- **任务优先级**：拆分3个优先级队列（高/中/低），付费用户/高优业务走高优队列
- **超时阈值**：标准图（1024×1024）超时30s，高清图超时60s，超时时自动终止并释放GPU资源
#### 风险卡点
- 任务积压导致Temporal调度压力过大 → 队列长度设置上限，超上限直接返回「系统繁忙」，触发扩容
- 工作流版本迭代不兼容 → 严格遵循Temporal版本化规范，旧版本保留至无运行中任务再下线
#### 验收标准
- 任务失败自动重试，不丢失、不重复执行
- 任务状态与前端推送、数据库记录三者一致
- 支持每秒1000+任务提交，调度无延迟

### 3. GPU 调度层（基础版）
#### 核心交付
- 中心化调度器：任务队列 + Worker节点管理 + 分发路由
- GPU节点心跳机制：节点每10s上报状态（GPU利用率、显存、运行中任务数）
- 异构GPU分池：拆分「H100高性能池」与「5090通用池」，高清/批量任务走H100，普通任务走5090
- K8s 基础Worker节点组部署：两档GPU各部署最小规模节点组
#### 关键技术决策
- **调度架构**：初期采用**中心化调度**（单调度实例），快速落地、逻辑简单；后续规模扩大再演进为分布式调度
- **任务粒度**：单卡单Batch推理，Batch大小由推理节点根据显存动态调整，调度层不感知具体Batch
- **故障迁移**：节点心跳超时30s，自动标记为故障，其上运行的任务由Temporal触发重试，重新调度
#### 风险卡点
- 中心化调度器单点故障 → 调度器做主备部署，状态存在Redis，故障秒级切换
- GPU资源碎片化 → 按模型类型固定分配GPU池，避免不同模型频繁切换加载
#### 验收标准
- 任务可正确路由到对应GPU池执行
- 节点故障后任务自动迁移，成功率不受影响
- 调度延迟 < 100ms

### 4. 推理与存储层
#### 核心交付
- 推理服务封装：FastAPI 封装 Diffusers 推理引擎，内置基础模型与常用LoRA
- 模型预加载：GPU节点启动时自动加载常驻基础模型，冷启动时间 < 30s
- 存储体系：原图存 AWS S3（同区域），开启CDN加速；任务元数据存 Postgres
#### 关键技术决策
- **推理引擎选型**：生产环境用 TensorRT 加速模型，优先保障吞吐；开发环境用原生Diffusers，兼顾迭代速度
- **数据生命周期**：原图保留7天，热门结果缓存30天，过期自动清理，控制存储成本
#### 风险卡点
- 模型冷启动慢导致任务超时 → 核心模型常驻显存，新增模型提前预热
- S3读写拖慢整体耗时 → 同区域部署，开启S3传输加速，大文件分片上传
#### 验收标准
- 单张1024×1024图平均生成耗时 < 5s（5090）/ < 2s（H100）
- 生成结果可通过URL正常访问

## Phase 2：Week 2 —— 生产化能力建设与灰度切流
**核心里程碑**：具备高可用、弹性伸缩、可观测的生产级能力，完成50%线上流量切迁，稳定承接业务。

### 1. 调度层升级：批量推理与弹性伸缩
#### 核心交付
- 动态批量推理（Dynamic Batching）：推理节点聚合时间窗口内的请求，凑成一个Batch统一推理
- GPU自动弹性伸缩：基于「队列等待时间 + GPU平均利用率」双指标，分钟级扩缩容节点
- 错峰调度：低峰期（夜间）自动调度批量离线任务，提升资源利用率
#### 关键技术决策
- **吞吐-延迟平衡点**：动态Batch最大等待窗口=200ms，超过窗口即使Batch没凑满也立即执行，保障用户体验
- **扩缩容策略**：GPU利用率>70%且队列等待>1s → 扩容；GPU利用率<30%且队列空 → 缩容；扩容冷却5分钟，缩容冷却15分钟
- **抢占机制**：暂不做任务抢占，通过优先级队列保障高优任务先执行；后续规模扩大再迭代
#### 风险卡点
- 批量推理导致尾部延迟飙升 → 高优任务跳过批量，直接单任务执行
- 扩缩容抖动 → 设置最小节点数保底，避免缩容到0
#### 验收标准
- GPU平均利用率从基线提升至 ≥ 60%
- 峰值流量下自动扩容，队列等待时间 < 2s
- 整体吞吐量提升 ≥ 80%（对比Week 1单任务模式）

### 2. tRPC 接入层稳定性增强
#### 核心交付
- 服务降级策略：高峰时自动降级非核心参数（推理步数-20%、分辨率降一档）
- 熔断机制：下游GPU错误率>5%时，接入层快速熔断，返回降级结果或友好提示
- 接入层全链路压测：验证峰值QPS下的稳定性
#### 关键技术决策
- **降级触发条件**：队列等待时间>3s 或 GPU利用率>85%，自动触发降级
- **降级顺序**：先降推理步数 → 再降分辨率 → 最后限制非付费用户提交频率
#### 风险卡点
- 降级幅度过大影响用户体验 → 分级降级，每一级都做灰度验证
- 熔断误触发 → 设置连续错误数阈值，避免偶发故障触发熔断
#### 验收标准
- 峰值流量下系统不雪崩，核心功能可用
- 降级策略可通过配置动态开关，无需重启服务

### 3. 可观测性与告警体系
#### 核心交付
- 黄金指标监控：
  - 接入层：QPS、延迟P50/P95/P99、错误率、限流次数
  - 调度层：队列长度、等待时间、调度成功率、节点数
  - GPU层：利用率、显存占用、单卡吞吐、故障次数
  - 业务层：每日生成量、成功率、平均耗时
- 分级告警体系：P0（紧急）/P1（重要）/P2（提示），对应不同通知渠道
#### 关键技术决策
- **监控选型**：Prometheus + Grafana 做指标监控，配合AWS CloudWatch做基础设施监控
- **链路追踪**：tRPC 集成 OpenTelemetry，实现全链路可追踪，问题可定位
#### 风险卡点
- 指标过多导致告警泛滥 → 只定义10个以内核心告警，其余做观测
- 监控数据丢失 → 核心指标做双副本存储
#### 验收标准
- 核心指标100%覆盖，可视化大盘可用
- P0告警响应时间 < 5分钟，准确率100%

### 4. 灰度切流
#### 核心交付
- 新旧系统并行，流量按比例切分
- 切流路径：1%流量验证 → 10%流量观察 → 50%流量全量验证
- 回滚预案：一键切回旧系统，数据零丢失
#### 关键技术决策
- **切流维度**：按用户ID哈希切分，保证同一用户始终走同一系统，避免体验不一致
- **回滚触发条件**：错误率>1%、P95延迟>10s、GPU利用率>90%持续5分钟，满足任一立即回滚
#### 风险卡点
- 切流后出现隐蔽问题 → 每一级切流观察至少30分钟，确认指标正常再下一步
- 新旧系统数据不一致 → 统一Postgres数据源，两边共享同一张任务表
#### 验收标准
- 50%线上流量稳定运行24小时
- 核心指标优于或持平旧系统
- 回滚操作可在1分钟内完成

## Phase 3：Week 3 —— 深度优化与全量上线（稳态阶段）
**核心里程碑**：成本优化达标，架构固化，100%流量切换，完成旧系统下线。

### 核心交付
1. **成本优化**：模型FP8量化上线，验证质量无损；热门LoRA常驻显存，冷门动态加载；GPU利用率提升至 65%-75%
2. **架构固化**：输出完整架构设计文档、运维手册、故障排查SOP、未来6个月容量规划
3. **全量切流**：100%流量切换至新架构，旧系统保留7天观察期后下线
### 验收标准
- 全量流量稳定运行72小时无重大故障
- 单图平均成本下降 ≥ 30%（对比Week 1）
- 整体服务可用性 ≥ 99.9%

## 架构师重点关注：5个顶层决策与风险预案
### 1. 不可下放的核心决策
1. **调度架构演进路线**：中心化→分布式的节点阈值与时间表
2. **质量-成本平衡点**：模型量化精度、降级幅度的业务接受标准
3. **资源配额策略**：不同业务线/用户等级的GPU资源分配规则
4. **故障熔断阈值**：各级别故障的熔断与降级触发条件
5. **数据合规策略**：用户生成内容的保留期限、隐私处理规则

### 2. Top 5 风险与应对预案
| 风险场景 | 影响等级 | 应对预案 |
| --- | --- | --- |
| 峰值流量突增，GPU排队爆炸 | P0 | 1. 自动弹性扩容；2. 触发分级降级；3. 队列设置上限，超上限直接限流 |
| 批量推理导致尾部延迟劣化 | P1 | 1. 高优任务跳过批量；2. 动态调整最大等待窗口；3. 单独设置高优GPU池 |
| 模型迭代快，架构频繁变动 | P1 | 1. tRPC网关层做接口兼容；2. 模型版本灰度发布；3. 旧版本保留回滚窗口 |
| GPU节点大面积故障 | P0 | 1. 多可用区部署节点组；2. 故障自动迁移；3. 触发服务降级，保障核心功能 |
| GPU成本超支 | P2 | 1. 利用率监控与告警；2. 错峰调度离线任务；3. 低峰自动缩容至最小节点数 |
