### 先总述：三个项目背后的统一技术逻辑
这三个Example Projects不是孤立需求，而是**「接入层tRPC + 任务编排Temporal + 算力调度AWS GPU + 数据层Postgres/S3」** 这套技术体系在三个不同业务场景的落地。tRPC是贯穿所有项目的统一API总线，负责承接前端交互、屏蔽底层复杂度、保证类型安全；下层的Temporal、GPU调度器、模型推理引擎负责实际的AI算力执行。

下面逐个深度拆解，从架构分层、tRPC的核心角色、技术难点、落地细节四个维度展开，完全对齐他们的官方技术栈。

## 项目一：从零搭建实时AI视频通话，端到端延迟<200ms，一周上线
### 核心目标
不是普通的音视频通话，是**带AI实时处理的视频通话**（比如实时换脸、美颜、背景生成、画质增强等），要求视频帧经过AI模型处理后，端到端整体延迟控制在200ms以内，且从0到1一周内完成上线。

### 完整技术架构（分层拆解）
```
┌──────────────────────────────────────────────────────────┐
│ 前端层：React + WebRTC + tRPC Client (WebSocket)        │
│  视频采集/渲染、音视频流处理、AI参数实时调节             │
└─────────────────────┬────────────────────────────────────┘
                      │ 信令走tRPC WebSocket / 媒体流走WebRTC UDP
┌─────────────────────▼────────────────────────────────────┐
│ 信令层：Next.js + tRPC Server (Subscription)             │
│  通话控制、AI指令下发、状态同步、质量上报、鉴权计费       │
└─────────────────────┬────────────────────────────────────┘
                      │ 内部RPC / 低延迟消息队列
┌─────────────────────▼────────────────────────────────────┐
│ 媒体处理层：AWS边缘GPU节点 + 自研AI模型 + WebRTC SFU      │
│  视频帧实时推理、帧编码/解码、媒体流转发、批量处理         │
└──────────────────────────────────────────────────────────┘
       数据持久化 ↓
     Postgres（通话记录、用户配置、计费数据）
```

### tRPC 的定位与具体职责
**tRPC不传输媒体流**（视频/音频流走WebRTC UDP协议，保证最低延迟），它承载的是**整个通话的控制面与信令面**，这是能一周上线的核心原因：
1. **通话全生命周期信令**：发起呼叫、接听、拒绝、挂断、成员变更，全部定义为tRPC Procedure，替代传统手写WebSocket协议，自带类型校验，不用反复对齐前后端字段。
2. **AI能力实时控制**：切换AI特效、调整参数（比如美颜等级、换脸模型、背景风格）、开关AI处理，通过tRPC双向实时下发，参数变更毫秒级生效。
3. **状态与质量同步**：网络延迟、丢包率、GPU负载、AI处理帧率等指标，通过tRPC Subscription实时推送给前端，用于动态调整码率和AI精度。
4. **业务逻辑收口**：鉴权、计费、通话记录落库，都在tRPC中间件层统一处理，业务逻辑和媒体处理完全解耦。

### 关键技术难点与落地方案
#### 1. 端到端<200ms延迟的拆解与控制
- **信令延迟 <10ms**：tRPC复用WebSocket长连接，没有HTTP握手开销，信令从前端到后端再到对端，单程控制在5ms以内。
- **传输延迟 <80ms**：AWS边缘节点就近接入，WebRTC P2P优先，无法P2P时走同区域SFU转发，跨国场景用全球骨干网。
- **AI推理延迟 <100ms**：
  - 模型侧：TensorRT量化加速、FP16推理、算子融合；
  - 工程侧：跳帧处理（关键帧全量处理，非关键帧轻量化处理）、流水线并行（解码→推理→编码重叠执行）；
  - 硬件侧：H100/B200的视频编解码硬件加速，直接读写显存，避免CPU内存拷贝。
- **端侧渲染 <10ms**：Canvas/WebGL直接渲染解码后的帧，避免DOM重排。

#### 2. 一周上线的工程可行性
- 信令层完全基于tRPC搭建，不用从零设计WebSocket协议、不用写序列化反序列化、不用对齐前后端字段，开发效率提升3倍以上；
- 媒体层复用开源WebRTC SFU（如Pion）+ AWS GPU基础镜像，不用从零搭建算力环境；
- AI模型复用内部已有的扩散模型能力，只做实时适配，不用重新训练。

## 项目二：调度数百张GPU，支撑每日数百万次图像生成
### 核心目标
构建高吞吐、低成本、高可用的AI图像生成服务，管理数百张异构GPU（5090、H100、B200），每日处理百万级生图请求，保证稳定性与资源利用率。

### 完整技术架构
```
┌──────────────────────────────────────────────────────────┐
│ 接入层：Next.js + tRPC Server                            │
│  请求接收、参数校验、任务状态查询、结果推送               │
└─────────────────────┬────────────────────────────────────┘
                      │
┌─────────────────────▼────────────────────────────────────┐
│ 任务编排层：Temporal + Postgres                           │
│  任务幂等、重试、超时控制、状态持久化、工作流编排         │
└─────────────────────┬────────────────────────────────────┘
                      │
┌─────────────────────▼────────────────────────────────────┐
│ GPU调度层：自研调度器 + AWS EKS (K8s)                     │
│  异构GPU调度、批量推理打包、弹性扩缩容、故障迁移           │
└─────────────────────┬────────────────────────────────────┘
                      │
┌─────────────────────▼────────────────────────────────────┐
│ 推理层：GPU节点 + 自研扩散模型 + LoRA权重                 │
│  批量推理、显存优化、模型热加载                             │
└─────────────────────┬────────────────────────────────────┘
                      │
              S3存储生成图 / Postgres存任务元数据
```

### tRPC 的定位与具体职责
tRPC是整个生图服务面向业务和前端的唯一入口，核心解决「高并发下的接入效率与参数正确性」问题：
1. **统一接入与强类型校验**：所有生图请求（prompt、尺寸、步数、CFG、LoRA选择、风格参数）都通过tRPC Mutation提交，Zod + 类型系统双重校验，从源头拒绝非法参数，避免无效请求浪费昂贵的GPU资源。
2. **批量请求合并**：利用tRPC的`httpBatchLink`能力，前端的多个并行请求会合并成一个HTTP请求到达服务端，大幅减少连接数和网关开销，高并发下效果显著。
3. **状态实时推送**：生图是秒级任务，通过tRPC Subscription实时推送生成进度、排队位置、完成状态，替代传统的前端轮询，降低服务端压力，同时体验更好。
4. **多模型路由屏蔽**：前端只需要调用统一的`generateImage`接口，底层是基础模型还是LoRA、是哪个版本，完全由tRPC服务端路由，业务层无感知。

### 关键技术难点与落地方案
#### 1. 数百万日请求的成本与吞吐优化
- **批量推理（Batch Inference）**：调度器把多个用户的请求打包成一个batch送入GPU推理，是提升GPU利用率、降低成本的核心手段。通过动态调整batch size，在延迟和吞吐量之间做平衡。
- **异构GPU分级调度**：
  - H100/B200：高分辨率图、批量大任务、LoRA训练，主打高吞吐；
  - 5090：普通分辨率、单张请求，主打低延迟低成本；
  - 调度器根据任务类型自动分配对应GPU池，整体资源利用率提升40%以上。
- **显存优化**：模型权重共享显存、LoRA动态加载卸载、FP8量化，单卡能同时承载更多并发请求。

#### 2. 高可用与弹性伸缩
- **Temporal兜底**：所有生图任务都由Temporal工作流管理，GPU节点故障、推理超时、排队溢出都会自动重试与迁移，保证任务不丢失。
- **秒级弹性扩缩容**：基于排队长度和GPU利用率，AWS Auto Scaling分钟级扩缩容GPU节点，峰值自动扩容，低谷自动缩容，控制成本。
- **多级降级策略**：流量高峰时，自动降低非关键请求的分辨率、减少推理步数、延长排队时间，优先保障核心用户体验。

#### 3. tRPC与Temporal的配合范式
这是他们技术栈里非常经典的组合模式：
1. 前端通过`tRPC.mutation`提交请求，服务端立即返回`taskId`；
2. 服务端同步调用Temporal启动异步工作流，自己不执行耗时操作；
3. Temporal工作流调用GPU调度器，排队、执行、回调更新状态；
4. 状态变更时，服务端通过`tRPC.Subscription`主动推送给前端；
5. 整个链路完全异步、解耦，接入层无状态，可以水平无限扩展。

## 项目三：LoRA与自研模型的测试与生产化，服务千万级用户
### 核心目标
建立AI模型从训练到上线的全流程工程化体系，支持LoRA和自研模型的快速测试、灰度发布、效果评估、迭代优化，在千万级用户规模下稳定迭代，不影响线上业务。

### 完整技术架构
```
┌──────────────────────────────────────────────────────────┐
│ 业务层：前端 / 业务方 通过 tRPC 调用模型能力              │
└─────────────────────┬────────────────────────────────────┘
                      │
┌─────────────────────▼────────────────────────────────────┐
│ 模型网关层：tRPC中间件 + 模型路由器                       │
│  版本管理、流量切分、参数兼容、灰度发布、效果埋点           │
└─────────────────────┬────────────────────────────────────┘
                      │
┌─────────────────────▼────────────────────────────────────┐
│ 推理服务层：多模型多版本共存部署                           │
│  基础模型、各类LoRA、不同版本实例，按流量分配               │
└─────────────────────┬────────────────────────────────────┘
                      │
┌─────────────────────▼────────────────────────────────────┘
│ 质量与观测层：自动化测试流水线 + A/B测试 + 全链路监控      │
│  基准测试、效果评估、指标监控、告警、数据回流               │
└──────────────────────────────────────────────────────────┘
```

### tRPC 的定位与具体职责
tRPC是模型服务和业务之间的**防腐层与兼容层**，核心解决「模型快速迭代与业务接口稳定」的矛盾：
1. **接口一致性保证**：无论底层模型怎么升级、LoRA怎么新增，对外的tRPC接口类型保持兼容。新增参数全部设为可选，废弃参数通过中间件做默认值填充，业务方无需改动代码。
2. **灰度发布与流量切分**：通过tRPC中间件实现流量灰度，支持按用户分桶、按比例分流、按业务场景路由。比如新LoRA先放1%流量，观察指标没问题再逐步放大，全程不用改前端。
3. **效果数据自动关联**：用户的每一次请求、生成结果、后续的点赞/踩/删除反馈，都通过tRPC上下文关联到具体的模型版本和LoRA ID，自动沉淀效果数据，驱动模型迭代。
4. **多租户与权限控制**：不同业务方、不同等级的用户，通过tRPC中间件分配不同的模型权限、配额和优先级，底层模型服务不用感知业务逻辑。

### 关键技术难点与落地方案
#### 1. 模型生产化的标准流水线
- **提交阶段**：新模型/LoRA提交后，CI自动跑基准测试：
  - 性能指标：吞吐量、延迟、显存占用；
  - 质量指标：FID、CLIP得分、人工标注打分；
  - 不达标自动打回，不进入发布流程。
- **灰度阶段**：
  - 内部灰度→1%流量→10%流量→全量，每一步都有明确的指标门槛；
  - Temporal调度批量回归测试，验证新模型对历史用例的兼容性。
- **全量阶段**：逐步替换旧版本，旧版本保留两周回滚窗口，确认无问题再下线。

#### 2. 千万级用户下的多模型管理
- **模型热加载**：GPU节点不重启，动态加载/卸载LoRA权重，秒级切换，不用停机发布。
- **请求智能路由**：简单请求（常规prompt、标准尺寸）自动路由到轻量模型/低精度版本，复杂请求路由到大模型，在保证效果的前提下最大化降低成本。
- **故障隔离**：单个模型/LoRA出问题，只影响对应流量，不会拖垮整个服务；tRPC网关层自动熔断，快速切回稳定版本。

#### 3. 数据闭环与快速迭代
- tRPC接口统一采集请求参数、生成结果、用户行为反馈；
- 数据回流到训练侧，自动挖掘bad case，持续优化模型和LoRA；
- 形成「上线→采集→优化→再上线」的闭环，模型迭代周期从周级缩短到天级。

### 最后：tRPC在CoreFlow体系里的核心价值总结
这三个项目从实时到批量、从接入到模型，之所以都选择tRPC而不是REST/GraphQL，本质是匹配他们「高速迭代、全栈TS、AI场景复杂」的特点：
1. **开发速度**：不用写接口文档、不用生成类型、不用前后端对齐字段，需求变更一天就能全链路上线，匹配创业公司的节奏；
2. **稳定性**：端到端类型校验，参数错误在开发阶段就暴露，避免线上因为参数问题导致GPU资源浪费、业务故障；
3. **统一范式**：查询、提交、流式、订阅，所有AI场景都用同一套API范式，团队学习成本低，代码复用度高；
4. **生态兼容**：和Next.js、React、Temporal、AWS都能无缝集成，刚好匹配他们的完整技术栈。
